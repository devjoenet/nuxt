# Verification And Delivery Checks

- Use this sequence: scoped startup → implementation with focused tests → review and fixes → one final verification pass → package consumer check when applicable → PR and user-testing handoff. Make routine implementation choices autonomously; ask only for missing authorization, consequential ambiguity, or a blocker that cannot be resolved safely from available evidence. Existing secret-setup and owner acceptance gates still apply.
- Read applicable rules and skills once per task and load supporting sections only as needed. Search and read bounded file ranges; summarize long command output and inspect full failure logs only when needed. Reuse current context instead of repeatedly loading complete plans, files, or logs.
- Before implementation, map the applicable package/host delivery scripts and CI checks in the existing task evidence, including aggregate-script overlap. Frontend changes must run the host's applicable frontend architecture gate, including installed package sources; targeted formatter/linter success does not replace `yarn lint:check`. Do not bypass SFC budgets or invent exceptions to avoid a failure.
- Before the module-merge checkpoint, run the complete applicable host delivery gates against the local package candidate, in addition to required package/consumer checks. Fix package-owned failures before opening upstream PRs. Disclose any blocked host gate at the checkpoint; module-local success alone does not establish host readiness.
- Keep one concise verification ledger in the existing task evidence, recording each check's scope, source revision or tree, dependency/environment inputs, result, and pending gates. Reuse it for PR descriptions and the Development handoff instead of maintaining duplicate narratives. Do not create a new documentation artifact solely for this ledger.
- During implementation, run the narrowest meaningful tests for changed behavior and important failure modes. After review fixes, run the required final gates once, accounting for their included checks instead of repeating passing constituents. Rerun a passing check only when changed code, dependencies, configuration, or environment invalidate its evidence. Copy-only documentation follow-ups do not restart application tests; executable configuration and generated-code changes still require affected checks.
- Reuse package and host evidence when the merged package tree matches the tested tree and relevant dependency/environment inputs remain equivalent; after remote dependency resolution, select the affected install/integration checks rather than restarting every suite. Verify fetched revisions and record why each post-merge check remains valid or must run again. Do not treat a matching source tree alone as proof of an equivalent install.
- Do not create, serve, or activate an isolated interactive preview unless the owner explicitly requests one. Preserve the regular application and Development database. Automated tests and independent package consumers must use disposable databases and synthetic data; this isolation remains required.
- For package extraction or distribution changes, use one reusable independent consumer per compatible dependency lane, reset to a known clean state, and perform one final authenticated archive/dist install without local paths. Exercise production `--no-dev` and cache behavior when the changed package affects them. Do not repeat an unchanged consumer setup for every intermediate edit or turn an automated consumer into a preview site.
- Select browser checks for changed user-visible behavior and risk. On a harness/setup failure, diagnose and fix the cause before rerunning; after two unsuccessful diagnosis attempts, report the specific blocker and continue independent checks instead of repeatedly rerunning the suite. Keep unverified browser behavior explicit at handoff.
- Keep required local checks and security, authorization, consent, transaction, reminder, and package-isolation regression coverage. Let hosted CI cover the full supported OS/PHP/dependency matrix; run a local compatibility lane when changed constraints or a known compatibility risk warrant it. Report unrun lanes accurately and stop after the user-testing handoff.

## Review evidence

Report the exact command/scope, revision or inputs, results, and omitted, blocked, or failing gates in the existing verification ledger. A passing targeted linter does not establish a passing repository lint gate. Guidance-only changes require instruction, link, and generated-output validation; run a documentation contract check when required.
