# Package Integration

Read verification-and-delivery-checks before selecting checks. For live Development work, also read development-delivery.

- The application lives at `/Users/joey/sites/nuxt`; local Composer package repositories live at `/Users/joey/code/packages` (`~/code/packages`). Keep each package in its own repository there, with its own dependencies, tests, branches, and release history. Run commands from the repository they affect and inspect its guidance and working tree first.
- `/Users/joey/code/packages/package-skeleton` is the reusable Laravel starter. Preserve it as a template; create a separate package checkout before installing dependencies or configuring a new package. Inspect and preserve local template modifications when preparing the new checkout; a Git clone alone does not copy uncommitted changes.
- Read the template's `README.md`, `AGENTS.md`, `AGENTS_PACKAGE.md`, `composer.json`, and `configure.php` before scaffolding. Its Composer install/update hooks run the one-time configuration script, which replaces placeholders, prunes files and dependencies, replaces README/agent guidance, and deletes itself after success. Use `composer install --no-scripts --no-interaction` in the new checkout when configuration needs to be controlled explicitly, then run `php configure.php --no-interaction` with deliberate metadata, feature, and tool options. Review the JSON result and follow-up steps.
- Supply the intended Composer vendor/package name, author details, namespace, class name, and description rather than accepting inferred Git/directory defaults. Confirm available options in the current script. Omitting all feature flags includes every feature; selecting feature flags includes only those features. Tool flags work independently the same way. Do not assume omitting a flag disables that feature or tool.
- Follow the configured package's own `AGENTS.md` and `.agents/skills`: `package-scaffold` for capabilities/provider wiring, `package-testing` for Pest/Testbench coverage, `package-compatibility` for constraints and CI, `package-release` for releases, and `package-generate-skill` for consumer-facing Boost guidance. Use `skeleton-development` only when changing the starter itself. Keep consumer guidance under `resources/boost/skills` distinct from maintainer skills; do not duplicate all package skills into this app.
- PHP 8.5 is the baseline for our starter and local Composer packages. Keep each package's Composer constraint, CI matrix, generated guidance, and compatibility skill aligned with that baseline. Determine Laravel and dependency support from the actual package manifest and CI rather than inheriting this application's versions; the current skeleton supports Laravel 12/13.
- Keep reusable behavior and its tests in the package, with application-specific integration in the host. Packages must not depend on this application's `App\\` namespace, local database contents, or absolute filesystem paths. For modular extractions, inspect the live task and existing host contracts before moving code.
- For local host integration, use a narrowly scoped Composer path repository pointing to the specific package checkout, with symlinking enabled and an explicit compatible development version where needed. Edit package source in its repository, never in the application's `vendor/`. Review Composer changes and update only the affected dependency set. Keep machine-specific paths and local-only lock resolutions out of shared/deployment changes; committed dependencies must resolve in clean CI and Forge installs without `~/code/packages`.
- Validate package behavior independently with its declared scripts: `composer test` runs static analysis, formatting checks, type coverage, and Pest tests in this starter. Use `composer build` for Testbench workbench verification when relevant; inspect its configuration first because the starter build wipes and migrates the workbench database. Keep workbench storage/database isolated from the application's environment. This Herd-served application does not need another server; use the package's `composer serve` only when a separate workbench preview is needed.
- Run relevant host integration checks as well as package tests. A symlinked local install does not prove a release/dist install works: verify a clean consumer without local paths before claiming package readiness, and report unrun PHP/Laravel/OS/dependency CI lanes separately. Keep branch/PR links associated with the correct repository and live Development task when work spans repositories.

## Integration verification

- Before the module-merge checkpoint, run the complete applicable host delivery gates against the local package candidate, in addition to package/consumer checks. Fix package-owned failures before upstream PRs; disclose blocked host gates.
- Reuse one disposable independent consumer per compatible dependency lane. Perform a final authenticated archive/dist install without local paths; exercise production --no-dev and cache behavior when affected.
- Reuse pre-merge evidence only when source, dependency, and environment inputs remain equivalent. Remote dependency resolution requires affected install/integration checks; a matching source tree alone is insufficient.
